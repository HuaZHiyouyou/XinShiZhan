## 1. 项目概述

### 1.1 我们要解决的问题

现实里很多情绪没有出口：深夜的失落、说不出口的委屈、突然的自责。它们往往不是需要「被解决」，
而是需要**被看见一次**。心事站把这件事做得尽可能轻：匿名表达、即时回应、机制上保护隐私。

### 1.2 设计原则

| 原则 | 落地方式 |
| --- | --- |
| **表达零门槛** | 匿名身份由系统分配，昵称可自取；注册只需用户名 + 密码 |
| **回应有实感** | 弹幕、留言、点赞、通知构成完整的即时反馈回路 |
| **安全靠机制** | 加密通道、限流锁定、审计留痕，而不是靠用户自觉 |
| **规则摆在明面上** | 所有开关、阈值都在后台可见可调，默认值写在文档里 |
| **不替用户做决定** | 密码只守长度底线，强度**建议**而非强制；做真实的人而不是完美的数据 |

### 1.3 技术选型

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 前端 | React 18 + TypeScript + Vite + Zustand | 类型安全、构建快、状态轻量 |
| 后端 | Node.js + Express | 与前端同语言，部署简单 |
| 数据库 | `node:sqlite`（Node 内置） | 零外部依赖、单文件、够用的并发；无需安装数据库服务 |
| 实时交互 | 弹幕墙 + 轮询 | 避免长连接带来的一致性与资源成本 |

## 2. 功能特性

### 2.1 用户侧

**表达**
- 匿名发布心事：心情标签、配图、话题标签
- 头像上传前可圆形裁剪（拖动 / 缩放），所见即所得
- 可见范围（公开 / 仅自己）、定时发布、自动过期
- 全站弹幕墙：颜色、特效、舒缓 / 密集两档密度、可暂停
- 留言（支持楼中楼）、点赞、举报；留言与站内信**自动同步**，不用手动刷新

**被发现**
- 热门 / 最新榜单，日 / 周 / 月 / 全站维度
- 音乐电台与全局播放器
- 站点概览看板

**账号**
- 用户编号 **UID**（注册即分配，全局唯一，从 `100001` 起）
- 自定义**昵称**，随时可改；清空则回到系统匿名身份
- 资料：简介、性别、生日、职业、所在城市、爱好、头像
- 账号安全：修改登录账号、修改密码（均需原密码确认）
- 登录页可勾选**记住账号 / 记住密码**
- 访客账号**严格只读**：能浏览全站，不能发言、点赞、留言或修改任何资料
- 邮箱 / 手机号 / 实名认证：**已预留，由超级管理员统一开关**

### 2.2 管理侧

**审批台（统一入口）**
- 内容审批：心事 / 留言 / 弹幕，支持单条与批量通过、驳回（附理由）
- 头像审批：可**放大查看 / 与当前头像并排对比**，显示范围可选缩略 / 中等 / 原图
- 举报处理：查看举报人填写的描述，忽略 / 删除被举报内容，**处理时写一句说明回执给举报人**
- 找回申请：查看、处理（**处理说明会同步到对方的站内信与找回记录**）、**直接为对方重置口令**

**站内回复**
- 站长（超级管理员）可按人群发站内信：全部正式账号 / 全部账号（含访客）/ 按角色 / 指定用户
- 支持常用模板、发送前预览人数、发送后报告未找到的收件人；每次发送都写入审计日志
- 权限收敛在服务端的单个函数里，后续放开给审核员或客服只需改一处

**用户与封禁**
- 搜索（用户名 / 昵称 / UID）、角色分配、违规计次
- 封禁预制时长：短时（1h / 1d / 3d）、长时（7d / 30d / 90d）、永久、自定义时间
- 协助重置密码、人工核验邮箱 / 手机号 / 实名
- 注册时间、注册 IP、最近登录时间与登录 IP 真实记录（IP 仅超级管理员可见）

**站点与安全**
- 注册 / 访客登录开关、访客发言开关、头像先审后显
- 身份验证开关（邮箱 / 手机号 / 实名，六项）
- 找回密码渠道开关与联系方式
- 安全策略阈值（登录失败、锁定、会话时长、各类限流、密码最小长度）
- 安全事件与锁定列表面板

**其他**
- 内容管理：检索、编辑、置顶、改状态、下架与回收站恢复
- 审核规则：自动审核开关、黑白词、频率上限、重复内容阈值
- 音乐库维护、全量操作审计日志

## 3. 快速开始

### 3.1 环境要求

| 项 | 要求 |
| --- | --- |
| Node.js | **≥ 22.5**（服务端使用内置 `node:sqlite`，推荐 22 LTS 或 24） |
| 操作系统 | Windows / macOS / Linux |
| 外部依赖 | **无**。不需要安装 MySQL、Redis 等任何服务 |

### 3.2 一键启动（Windows 推荐）

双击项目根目录的 **`一键启动.bat`**（或 `start.bat`）。脚本会依次完成：

1. 检查 Node.js 与 npm
2. 缺哪个依赖就装哪个（根目录 / server / web）
3. 构建前端产物（`web/dist` 不存在时）
4. 启动服务并自动打开浏览器

```bat
:: 强制重新构建前端
start.bat build

:: 指定端口
set PORT=8899 && start.bat
```

> 批处理文件以 GBK 编码保存以匹配中文 Windows 控制台；启动服务前会临时切换到 UTF-8
> 让服务端日志正常显示，退出后自动还原原代码页。

### 3.3 手动部署

```bash
npm run install:all   # 安装根 / server / web 三处依赖
npm run build         # 构建前端（产物由服务端直接托管）
npm start             # 启动服务，默认 http://localhost:8787
```

### 3.4 开发模式

```bash
npm run dev           # 同时起 server(--watch) 与 vite dev server，前端热更新
npm run dev:server    # 只起服务端
npm run dev:web       # 只起前端
```

> 开发时页面走 Vite Dev Server，**不读取 `web/dist`**；改完前端若要用 `npm start` 验证，需先 `npm run build`。

### 3.5 命令速查

| 命令 | 作用 |
| --- | --- |
| `npm run install:all` | 安装三处依赖 |
| `npm run dev` | 前后端并行开发模式 |
| `npm run build` | 构建前端产物 |
| `npm start` | 生产模式启动（托管 `web/dist`） |
| `npm run seed` | 写入演示数据（用户 / 心事 / 弹幕 / 音乐） |
| `npm run fresh` | 生成「只有超级管理员」的纯净实例数据（见 [10.4](#104-纯净实例与开源分发)） |
| `npm run oss:copy` | 生成可开源的干净副本 `XinShiZhan/`（见 [10.5](#105-生成开源副本)） |
| `npm run lint:hooks` | 前端 Hook 顺序静态检查（防「黑屏」类渲染崩溃） |
| `npm run verify:security` | 端到端安全验证，输出 44 项检查结果 |
| `npm run verify` | 先跑 Hook 检查，再跑端到端验证 |

## 4. 使用指南（用户）

### 4.1 账号

#### 注册

| 字段 | 说明 |
| --- | --- |
| 用户名 | 2–20 位中英文、数字、下划线，全局唯一 |
| 密码 | **至少 6 位**，≤ 128 位；右侧独立显隐开关 |
| 确认密码 | 需与密码一致；**拥有自己独立的显隐开关**，不会跟着密码框一起切换 |
| 昵称 | 选填，2–16 位中英文、数字、下划线或空格；留空由系统分配 |
| 邮箱 / 手机号 / 实名 | 仅当超级管理员开启对应开关时才出现 |

**密码策略（重要）**

> 本站只强制「长度底线」，**不强制复杂度**：
> - ✅ 可以包含用户名，例如用户名 `123`、密码 `123456` 是允许的
> - ✅ 常见口令（如 `123456`、`password`）**同样可以注册成功**
> - ✅ 有任何强度建议都只是**提示**，不阻止提交
>
> 输入密码时会实时显示强度条与改进建议（长度 / 大小写 / 数字 / 符号 / 是否与用户名相似 /
> 是否常见弱口令）。**建议使用强力密码，但普通密码同样可以通过。**
>
> 真正的兜底不在密码规则上，而在服务端：失败限流、临时锁定、工作量证明与登录审计。

注册成功后**立即分配用户编号 UID** 并直接登录。

#### 登录

1. 前端与服务端完成一次性 ECDH 握手，协商出本次会话专属密钥
2. 领取并求解工作量证明（PoW），用于抬高脚本成本
3. 密码在本地二次加密后随信封提交，服务端解密校验
4. 通过后下发 `httpOnly + SameSite=Strict` 会话 Cookie

> 首次登录因为需要解一道哈希题会稍慢（约几百毫秒），之后会明显更快。
> 连续失败会逐步提高难度并触发临时锁定，界面会显示剩余解锁时间。

#### 记住账号 / 记住密码

登录弹窗里有两个开关，**默认都是关闭的**：

| 开关 | 行为 |
| --- | --- |
| 记住账号 | 下次打开登录弹窗时自动填好用户名 |
| 记住密码 | 自动填好用户名与密码；勾选它会顺带勾上「记住账号」 |

两点必须说清楚：

- 只在**登录成功后**才写入，输错密码不会把错的密码留在本机；两个开关都关掉时会立即清除已存内容。
- 「记住密码」必然要把口令留在浏览器里。**任何纯前端方案都做不到真正的加密** ——
  页面自己能解开的密文，本机上能跑脚本的人也能解开。这里只做了一层混淆，
  作用是避免别人随手打开开发者工具就看到明文。**公共设备上请不要开启。**
- 界面上也写了同样的提示，不做「悄悄记住」。

#### 访客模式

当管理员开启「访客登录」后，登录弹窗底部会出现「以访客身份进入」。

**访客账号是严格只读的**，这是写在服务端的硬规则，不提供开关：

| 能做 | 不能做 |
| --- | --- |
| 浏览心事、留言、弹幕、榜单、音乐、站点概览 | 发布心事 / 留言 / 弹幕 |
| 查看自己的访客身份 | 点赞、举报 |
| 正常退出登录 | 修改昵称、头像、资料 |
| | 修改登录账号与密码 |
| | 上传图片、发起身份验证 |

前端在这些位置会直接显示「访客只能浏览」并给出注册入口，而不是让你点了才报错。
每次访客进入都会记录 IP 与设备信息，便于审计。

#### 个人信息

- **用户编号**：只读，全站唯一
- **昵称**：可修改；清空即回到系统分配的匿名身份。修改后全站展示名同步更新
- **资料**：简介、性别、年龄、生日、职业、所在城市、爱好、头像
- **头像**：开启「头像先审后显」时，新头像需管理员在审批台通过后才全站生效
- **身份验证**：开关开启后可填写邮箱 / 手机号 / 实名（姓名 + 证件号），
  实名资料**加密存储**；改动任一验证信息会使原认证状态失效，需重新核验

#### 账号与安全

| 操作 | 要求 |
| --- | --- |
| 修改登录账号 | 必须提供**当前密码**；需满足用户名规则且未被占用 |
| 修改密码 | 必须提供**当前密码**；新密码至少 6 位；两次输入一致 |

> 原密码、新密码输入框默认内容**不可见**（占位显示为 `****`）。
> 每个密码框右侧都有**独立的**显隐开关，图标表达的是**当前状态**：
> 睁眼 = 此刻是明文可见，斜杠眼 = 此刻是隐藏的。
> 确认密码与新密码各自独立切换，方便对照检查是否输错。
> 修改密码成功后，**除当前设备外的所有登录状态立即失效**。

#### 找回密码

登录页 →「忘记密码？」，四种渠道：

| 渠道 | 可用条件 | 说明 |
| --- | --- | --- |
| 站内客服 | 开关开启 **且** 已配置客服账号 | 未配置时按钮置灰并标注「未配置」 |
| 站长求助 | 开关开启 | 申请直接进入后台并站内通知站长，**不依赖外部联系方式** |
| 邮箱找回 | 开关开启 | 通道尚未接入，提交会明确提示「预留未接入」 |
| 密保找回 | 开关开启 | 位置已预留，尚未开放设置与校验 |

提交顺序校验：**填账号 → 渠道开启 → 账号真实存在 → 渠道可受理**，任一步不通过都会给出具体原因。
受理成功会返回**受理编号**并站内通知管理员。

**处理结果会在两处同时出现**：

| 位置 | 内容 |
| --- | --- |
| 站内信 | 标题 + 管理员填写的说明（没填则是一句通用结论） |
| 个人信息 →「**找回密码记录**」 | 受理编号、方式、状态、提交时间、**完整来源 IP**、处理人与处理说明 |

也就是说：找回是「离开账号」时发生的事，回来之后能在这里看到完整的时间线，
不用去翻站内信，也不会出现「站内信只说了已处理、看不到具体结论」。

### 4.2 内容

**头像**

- 上传前先裁剪：选好图片后弹出圆形裁剪框，**拖动调位置、滑杆或滚轮缩放**，
  圆里的内容就是最终头像；确认后导出 512×512 的方图再上传。
  带透明通道的 png / webp 会保留透明，其余压成 JPEG，体积小很多。
- 头像最终是圆形展示的，所以裁剪框也是圆的 —— 所见即所得，不会出现「传上去脸被切掉一半」。

**发布心事**
- 支持心情标签、话题标签与配图
- 可见范围：公开 / 仅自己
- 生命周期：立即发布 / 定时发布 / 设定过期时间
- 提交后进入自动审核；命中规则会转人工复核，驳回会附带理由并累加违规计数

**互动**
- **留言**：支持楼中楼回复；列表每 15 秒静默同步一次，别人刚回复就能看到
- **弹幕**：可选颜色与特效；有每分钟条数上限。密度分两档 ——
  「舒缓」同屏最多 9 条、速度 40–72 px/s；「密集」同屏最多 26 条、速度 96–168 px/s
- **点赞**：同一目标每人一次，可取消
- **举报**：先选原因，再补一段描述（选填，200 字），会进入管理端举报队列；
  处理后**一定会收到回执**，包含管理员写的说明

**弹幕墙的两档密度**

| 档位 | 同屏上限 | 速度 | 发射间隔 | 观感 |
| --- | --- | --- | --- | --- |
| 舒缓 | 9 条 | 40–72 px/s | 1.4–2.6 s | 慢悠悠飘过，看得清每一条 |
| 密集 | 26 条 | 96–168 px/s | 0.3–0.7 s | 快速刷过，热闹 |

两档都**保证同一条泳道里不会重叠**：只有当前一条的尾巴完全进了屏、且留出随机间距后，
才允许下一条进入这条泳道；六条泳道都没空位时，这一拍干脆不发，而不是硬挤进去。
每条泳道的速度会一直锁到它彻底空掉为止 —— 否则后一条速度更快就会追尾。

**密码输入框的约定**

- 每个密码框各有**自己的显隐开关**，确认密码不会跟着密码框一起被切换；
- 图标表达的是**当前状态**：睁眼 = 此刻明文可见，斜杠眼 = 此刻隐藏；
- **空框不显示开关**（只是不显示，位置照旧留着）—— 还没输入时那个眼睛会让人
  误以为「这里已经有密码了」，同时保留位置又能让同一排的输入框宽度完全一致；
- 原密码框的 `****` 是**占位提示**，表示「这个账号本来就有密码」，不是框里已有内容。

浏览器自带的密码显隐按钮（Edge 的 `::-ms-reveal` 等）已在样式里关闭，
不会和自己的开关同时出现。

### 4.3 通知与音乐

- 通知中心汇总：审核结果、留言、点赞、系统消息、找回申请处理结果
- **点击任意一条站内信可看全文**：列表里只放两行摘要，长说明点开看（打开即标记已读）
- **站内信自动同步**：登录期间每 20 秒拉一次，页面切回前台立刻补一次；
  铃铛、侧栏红点、站内信页面读的是同一份状态，任一处置为已读，其它地方立刻跟上
- 站长勾了「弹窗提醒」的公告，会在你**下次进站时**弹一次，关掉就不再出现
- 音乐电台支持后台维护曲库，全局播放器跨页不间断

## 5. 管理指南（管理员）

### 5.1 角色与权限

| 角色 | 代码 | 权限范围 |
| --- | --- | --- |
| **超级管理员** | `superadmin` | 站点所有者。可改站点级开关、角色分配、人工核验、封禁管理员。**只能由服务端自举，无法被授予或剥夺** |
| 管理员 | `admin` | 审核内容、处理举报、封禁普通账号、重置密码、查看访客与安全记录 |
| 审核员 | `reviewer` | 审批队列与内容处理；**看不到**站点级配置菜单 |
| 住客 | `user` | 发布、留言、弹幕、点赞 |
| 访客 | `guest` | 浏览（可发言由开关控制） |

#### 审核分层与制衡

角色有等级：**超管 3 > 管理员 2 > 审核员 1 > 住客 / 访客 0**。
所有处理类接口都要过同一道判定（`server/src/lib/permissions.js`），只有两条原则：

| 原则 | 说明 |
| --- | --- |
| **不对自己动手** | 自己发的内容、自己的头像、自己提交的举报、自己的找回申请、自己的账号，一律不能自己处理；**也不能举报自己的内容** |
| **不越级动手** | 只能处理等级**严格低于**自己的对象 —— 管理员管不了管理员，更管不了超管；审核员管不了管理员。越级的条目**根本不会出现在你的队列里**，而不是点了才报错 |

> 一句话概括：**超管审所有人（除自己），管理员审住客与审核员，审核员审住客。**

**唯一的例外是超管的「自我裁决」。** 他是站点所有者，上面没人 —— 如果他自己的内容
进了待审队列，全站就没人能处理，只能永远卡住。所以给他留了一条通道：

- 必须**逐条**处理，**批量不适用**（一条理由套很多条说不清楚，驳回时用户也收不到有意义的回执）；
- **理由选填** —— 写了会进审计日志、并随站内信一起送达，不写也放行（前端不挡按钮、服务端不校验）；
- 界面上标注「自我裁决」，审计日志里记为 `self: true`。

另外，一条举报**只能审判一次**：已处理的不能改判，避免反复翻案。

### 5.2 审批台

所有「待审 / 待处理」业务集中在一页的四个标签：

| 标签 | 可做操作 |
| --- | --- |
| 内容审批 | 单条 / 批量通过、驳回（可填理由，会通知作者并计违规） |
| 头像审批 | 点缩略图放大查看，可在「待审新头像 / 当前头像」间切换或并排对比，显示范围可选缩略 / 中等 / 原图；通过 / 驳回（理由可选） |
| 举报处理 | 查看举报描述 →「给举报人的说明」→ 忽略 / 删除（删除会二次确认） |
| 找回申请 | 标记已处理 / 驳回（均可填写给用户的说明）、**为对方重置口令** |

### 批量操作

四张表都支持**批量选择**（内容审批 / 内容管理 / 举报处理 / 用户管理）：每行左侧一个勾选框，
表头下方一条批量条（全选本页 / 清空 / 本页可用的批量动作 + 实时计数），选中的行会整行提亮。

| 表 | 批量动作 |
| --- | --- |
| 内容审批 | 批量通过 / 批量驳回（待人工复核时才出现） |
| 内容管理 | 批量下架（列表）/ 批量恢复（回收站），下架走二次确认 |
| 举报处理 | 批量忽略 / 批量删除被举报内容，共用同一个「给举报人的说明」弹窗 |
| 用户管理 | 批量封禁（原因 + 时长对整批生效）/ 批量解封 |

服务端每条批量接口都**逐条跑与单条完全相同的判定函数**（`applyPostTrash` / `applyReport` /
`applyBan`）—— 批量最容易写着写着就绕开权限，所以两边必须是同一份代码。
逐条结果的形状是 `{ done, blocked: [{ id, error }] }`：能动的照做，越权的单独报回，
前端如实告诉管理员「哪几条没动、为什么没动」，而不是笼统地说一句成功。

> 队列按角色分层：你能处理的目标才进你的队列。处理自己的内容属于「自我裁决」，
> 理由选填，详见 [5.1 审核分层与制衡](#审核分层与制衡)。

> 找回申请的「重置并交付新密码」会生成一次性临时密码，**只在响应中出现一次**，
> 并吊销该账号此前的全部登录态。请通过可靠渠道交付本人，并提醒其立即修改。

### 5.3 用户与封禁

**搜索**：按用户名、昵称或 UID。

**封禁**：三组预制 + 自定义

| 分组 | 选项 |
| --- | --- |
| 短时 | 1 小时 / 1 天 / 3 天 |
| 长时 | 7 天 / 30 天 / 90 天 |
| 永久 | 永久封禁（需手动解封） |
| 自定义 | 指定具体解封时间 |

封禁期间该账号无法发布、留言与弹幕，已登录设备立即掉线，登录时会看到原因。
常见封禁原因可一键填入，也可自行撰写。

**其他操作**：调整角色（仅超级管理员）、重置密码（仅超级管理员，不能重置自己）、
人工核验邮箱 / 手机号 / 实名（需对应开关已开启）。

### 5.4 站点与安全

| 分组 | 配置项 |
| --- | --- |
| 站点 | 开放注册、访客登录、访客发言、头像先审后显、每 IP 每小时访客上限、站点公告 |
| 身份验证 | 邮箱 / 手机号 / 实名的「开放」与「必填」共六项开关，**默认全部关闭** |
| 找回密码 | 四种渠道开关 + 客服账号 / 站长联系方式 / 自定义说明 |
| 安全策略 | 见 [6.2](#62-安全策略项) |
| 安全记录 | 会话中的锁定列表（可手动解锁）与最近的认证事件 |

配置保存后**立即生效**，无需重启：前端在登录弹窗打开时、后台保存后都会重新拉取站点配置。

### 5.5 身份验证与找回密码的预留说明

- 邮箱、手机号、实名的**数据结构、接口与开关都已就位**，但真实的验证码下发 / 实名核验通道尚未接入。
- 开关关闭时：用户侧不出现输入框，服务端对注册与资料写入直接拒绝（403），管理员也无法人工核验。
- 开关开启后：注册页与个人信息页均出现对应字段；触发验证会返回「通道尚未接入」的明确提示，
  接入真实服务后**前端无需改动**。
- 在此之前，认证状态由管理员在「用户与封禁」中**人工核验**。

### 5.6 站内回复

后台「站内回复」是给指定人群发站内信的地方，目前**只有站长（超级管理员）能发**。

| 收件人 | 说明 |
| --- | --- |
| 全部正式账号 | 所有注册用户，**不含访客**（默认选项） |
| 全部账号 | 含访客在内的一切账号 |
| 按角色 | 只发给某一个角色：住客 / 审核员 / 管理员 / 超级管理员 |
| 指定用户 | **从账号列表里搜索并勾选**（支持按昵称 / 用户名 / UID 搜），可多选，已选的人以 chips 显示 |

> 指定用户不是手打用户名 —— 拼错一个字母就会静默漏发，还不如看着账号挑。

**弹窗提醒（可选）**

勾上「下次进站时弹窗提醒」后，这封信会在收件人**下次打开站点时**弹出一次，关掉后不再弹。
刻意**不做即时弹窗**：正在写东西的人被一条公告打断，比晚几个小时知道更糟。
实现上是服务端取走即标记（`popup_seen_at`），所以关没关浏览器都只弹一次。

其他细节：

- 提供三套常用模板（维护通知 / 规范提醒 / 感谢回应），也可以自己写；标题 60 字、正文 600 字；
- 发送前会实时显示「将发送给 N 人」，指定用户时会列出找不到的名字；
- 一次最多 5000 人，插入包在事务里一次性提交；
- 每次发送都会写入审计日志（谁、发给谁、多少人、标题）；
- 权限判断收敛在服务端的 `canSendSiteMessage(user)` 一个函数里 ——
  以后要放开给值班审核员或客服，改这一处即可，接口与前端都不用动。

### 5.7 审核规则

自动审核开关、黑名单 / 敏感词、链接与图片是否需人工确认、新用户观察期、
每小时发布上限、重复内容相似度阈值、榜单热度权重等。
**内容策略属于站点级开关，仅超级管理员可改。**

### 5.8 审计日志

登录 / 注册 / 登出 / 资料变更 / 账号变更 / 找回申请 / 内容操作 / 角色与配置变更全部留痕，
记录操作者、目标、详情与时间。

### 7.2 请求生命周期

```
浏览器
  │  ① POST /api/auth/handshake  → ECDH 交换公钥，协商会话密钥
  │  ② POST /api/auth/challenge  → 领取 PoW 挑战
  │  ③ 本地求解 PoW + 封装请求信封
  ▼
Express
  ├─ securityHeaders        安全响应头、源码/映射/数据库探测拦截
  ├─ CORS 白名单
  ├─ apiRateLimit           全站粗粒度限流
  ├─ attachUser             尝试解析登录态（失败即游客）
  ├─ secureChannel          验签 → 解密 → 交给业务
  ├─ 权限闸门               requireAuth / requireSpeaking / requireStaff / requireSuperAdmin
  ├─ 业务处理               参数校验 → 自动审核 → 落库 → 审计留痕
  └─ 响应信封               加密 + 签名后回传
```

### 7.3 加密通道协议

| 环节 | 实现 |
| --- | --- |
| 密钥协商 | ECDH `prime256v1`，HKDF-SHA256 派生 `encKey` / `macKey` |
| 请求体 | 随机字段别名 + AES-256-GCM 加密 + HMAC-SHA256 签名 + 时间戳 + 一次性 nonce |
| 响应体 | 同一会话密钥加密并签名，前端先验签再解密 |
| 敏感字段 | 密码等字段在信封内**再加密一层**，密钥由本次请求 nonce 派生 |
| 防重放 | nonce 一次性；同一信封重复提交返回 409 |
| 强制通道 | 策略开启时，无合法会话的明文请求直接 428 |

### 7.5 动效层

动效集中在一个文件里（`web/src/styles/motion.css`）+ 一个状态源（`store/progress.ts`），
目标只有两个：**让等待有交代，让操作有实感**。不为了动而动。

| 场景 | 做法 | 为什么这么做 |
| --- | --- | --- |
| 页面切换 | 按 pathname 换 key，新页面淡入 + 上移 10px | 刻意**不做退场动画**：退场要等动画跑完才挂载新页面，每次点击都会多等 200ms |
| 加载进度 | 顶部 2px 进度条，由 `api/client` 每次请求进出打点 | 反映的是**真的有请求在跑**，不是「路由变了就假装加载」；<130ms 的请求不闪、已显示的至少留 320ms |
| 数据缓冲 | 骨架屏（`SkeletonList` / `SkeletonStats` / `SkeletonArticle` / `SkeletonThread`） | 占位与最终内容同构，数据到位是「填进去」而不是「换一屏」，不会跳 |
| 列表入场 | `.stagger` + `--i` 逐条浮入，延迟 35ms 递增并**封顶到第 8 条** | 长列表第 40 条不该等两秒，「加载感」会变成「卡顿感」 |
| 点击反馈 | `:active` 时按钮缩到 0.97、小图标缩到 0.9 | 比单纯变色明确得多，松手即还原 |
| 展开收起 | `.collapse` 用 `grid-template-rows: 0fr → 1fr` | 不需要预先知道内容高度，也不会像 `max-height` 那样把动画时间浪费在无效高度上 |

性能与可访问性约定：

- 只动 `transform` / `opacity`，避免触发重排；
- 所有动效都服从系统级「减弱动效」（`prefers-reduced-motion`），由 `base.css` 统一压制。

**哪些面板用实底，哪些保留玻璃**

| 面板 | 处理 | 原因 |
| --- | --- | --- |
| 弹窗、下拉菜单、留言抽屉 | **实底** `var(--surface)` | 它们会盖在别的内容上。半透明 + 模糊会让底下的卡片边界、深色配图透上来，看起来像「被下面那张卡片压住了一截」或「底部黑了一块」；而且这三处都要读字、要输入 |
| 内容卡片 | 保持玻璃质感 | 它们不遮挡任何东西，通透感是设计语言的一部分 |

留言抽屉还额外从「挤压」改成了「覆盖」：老实现给 `.app-body` 加 424px 右内边距，
等于把整个栅格压缩 400px（信息流变窄、右侧栏被挤到换行、正文截断）——
为了看留言把整页做变形不划算。现在它浮在右侧栏之上、从右边滑入，
宽度收在 `--drawer-w`（480px）里，音乐悬浮栏的让位距离也读同一个变量。

**浮层一律用 portal**

后台的弹窗走统一的 `Modal` 组件（`createPortal` 挂到 `document.body`）。原因和举报菜单一样：
祖先只要带 `transform` / `filter` / `backdrop-filter` 就会成为 `position: fixed` 的**包含块** ——
后台页面里到处是玻璃卡片与入场动画，弹窗渲染在卡片内部的话，遮罩只盖得住那张卡片
（看起来就是「卡片黑了一块」），位置也跟着卡片跑。挂到 body 之后遮罩铺满视口、弹窗对准屏幕中心，
整块背景（顶栏、侧栏、内容）一起模糊。

举报菜单挂在 `document.body` 上（`createPortal` + `position: fixed`，坐标实时量取）。
留在卡片里的话，卡片在**入场动画或悬停抬升时会带上 `transform`**，等于新建了一个层叠上下文，
里面的浮层 z-index 再高也压不过后面那些卡片 —— 表现就是「菜单被下一张卡片切掉一截」。
挂到 body 之后，祖先的 `transform` / `overflow` / `z-index` 都夹不住它；
面板本身只做位移不做淡入，永远不会出现「半透明那一帧」。

**分隔线在收**

全站不画分割线：卡片内部靠留白与底色分块，而不是一条横线。
已清掉的有站内信弹窗页脚、下拉面板页脚、头像查看器页脚、找回记录的处理说明、
日期选择器的时间行、站内回复发送条、举报补充说明的左侧色条、骨架屏行间线。
楼中楼只靠缩进区分层级，不再画竖线；留言抽屉里的「原文」也从通栏色带改成一张卡片，
并放进滚动容器 —— 往下翻留言时跟着滚走，而不是永远钉在顶部。

## 8. 安全设计

### 8.1 威胁与对策

| 威胁 | 对策 |
| --- | --- |
| 传输被窃听 / 篡改 | 一次性 ECDH 会话密钥 + AES-256-GCM + HMAC 签名；响应同样加密签名 |
| 请求被重放 | 一次性 nonce 校验，重复信封返回 409 |
| 数据库被拖走 | 密码 = 主密钥派生胡椒 + SHA-256 摘要 + bcrypt(12)；实名资料 AES-256-GCM 加密 |
| 凭证填充 / 暴力破解 | 按账号与 IP 双维度限流 + 临时锁定（倍增时长）+ 工作量证明 |
| 脚本批量注册 | 注册限流 + PoW + 蜜罐字段 + 弱口令提示（不拦截真实用户） |
| 会话被盗用 | 令牌短时效、可吊销、与服务端会话双向绑定；`httpOnly + SameSite=Strict + Path=/api` |
| CSRF | 同站 Cookie 策略 + 请求签名，跨站请求无法构造合法信封 |
| 账号枚举 | 登录失败统一提示；找回接口对账号是否存在给出明确但受限于限流的反馈 |
| 越权 | 服务端逐接口判定角色，站点级配置仅超级管理员可写；前端仅做隐藏 |
| 信息泄露 | 源码 / sourcemap / 数据库路径一律 404；错误响应不含堆栈 |
| 审计缺失 | 认证事件、内容操作、角色与配置变更全量留痕 |

### 8.2 密码与会话

- 密码**只做长度下限**（默认 6 位，可调），强度以提示形式呈现，不阻止提交。
- 存储：`bcrypt(sha256(pepper || ':' || password), 12)`，摘要化顺带解决 bcrypt 72 字节截断。
- 旧版明文 bcrypt 哈希在首次成功登录时**静默升级**。
- 会话默认 120 分钟滑动续期；改密后除当前设备外全部吊销。

### 8.3 防护层次

1. **网络层**：安全响应头、CORS 白名单、源码与敏感路径屏蔽
2. **通道层**：强制加密、验签、防重放、会话绑定
3. **接口层**：细粒度限流、PoW、蜜罐
4. **业务层**：角色闸门、参数白名单、自动审核
5. **数据层**：密码哈希 + 胡椒、字段级加密、令牌摘要
6. **审计层**：事件留痕、锁定记录、操作日志

## 9. 测试与验证

### 9.1 运行

```bash
npm run lint:hooks       # 静态检查：Hook 是否被写在提前 return 之后
npm start                # 另开一个终端保持服务运行
npm run verify:security  # 执行 44 项端到端检查

# 或者一条命令跑完
npm run verify
```

`lint:hooks` 检查的是一个 TypeScript 与接口测试都覆盖不到的坑：
**Hook 一旦出现在 `if (xxx) return` 之后**，弹窗打开 / 数据加载完成时 Hook 数量变化，
React 会直接卸载整棵组件树——表现为**整页黑屏**。该检查零依赖、毫秒级完成，
自测覆盖了 `if (...) return` 与 `if (...) { return }` 两种写法。

脚本通过**与前端完全相同的加密通道协议**直接打接口，覆盖握手、PoW、信封登录、会话续用、
攻击拒绝、业务规则与权限边界。可用环境变量覆盖：

| 变量 | 默认 |
| --- | --- |
| `E2E_BASE` | `http://127.0.0.1:8787` |
| `E2E_ADMIN_USER` / `E2E_ADMIN_PASS` | `huazhiyou` / 默认口令 |

### 9.2 覆盖范围（44 项）

- **通道与协议**（11 项）：别名可复现、PoW 求解与升级、报文无明文、Cookie 属性、
  请求头签名、刷新后续期、信封篡改 / 重放 / 冒用会话号被拒、明文直连 428
- **会话与权限**（5 项）：后台统计加密可读、安全面板、普通用户 403、未登录 401、登出即失效
- **安全响应**（4 项）：蜜罐命中、PoW 缺失 / 伪造、源码与数据库探测屏蔽、安全响应头
- **账号体系**（6 项）：UID 分配与唯一性、昵称修改与回落、账密修改、超级管理员角色不可变、
  普通管理员越权被拒、注册时间与 IP 真实记录
- **密码策略**（1 项）：6 位底线、含用户名与常见口令放行、5 位拒绝、公开配置一致
- **身份验证**（2 项）：关闭时全链路拒绝、开启后注册与资料可写
- **访客只读**（1 项）：浏览正常，改资料 / 改账号 / 发布 / 弹幕 / 点赞 / 举报一律 403 且理由一致
- **找回密码**（2 项）：账号必填 / 真实存在 / 渠道状态 / 工单落库 / 通知 / 处理闭环；
  处理说明同时回显到站内信与本人的「找回记录」，来源 IP 完整回显
- **举报回执**（1 项）：举报可带补充描述、管理端可见、处理说明回执给举报人并落库
- **站内回复**（1 项）：站长可按人群（全部 / 角色 / 指定用户）发送，普通管理员 403 被拒
- **权限分层**（4 项）：审核员不能越级审管理员；管理员不能封同级 / 自己 / 超管；
  越级条目不进队列；超管自我裁决（理由选填）不支持批量；举报不能自报、不能重复审判、
  举报人不能自己拍板；自己的内容能自己下架与恢复
- **后台批量**（1 项）：批量下架与恢复、批量处理举报（含已处理不可改判）、
  批量封禁与解封；混入越权条目时**能动的照做、越权的单独报回**，超管不可被封
- **弹窗提醒**（1 项）：勾了弹窗的信在下次进站可取到，取走即标记、再进不再弹；
  没勾的永远不进弹窗队列
- **封禁与重置**（2 项）：预制时长与永久 / 自定义、临时密码可用且旧密码失效
- **其他**（2 项）：连续失败锁定与解锁、公开接口可用

> 脚本会自动放宽限流阈值并在结束时还原，清理本轮创建的测试账号与记录。

## 10. 运维

### 10.1 备份与恢复

需要备份的文件：

| 路径 | 说明 |
| --- | --- |
| `server/data/xinshizhan.db`（含 `-wal` / `-shm`） | 全部业务数据 |
| `server/data/master.key` | 主密钥，**丢失将无法解密实名资料并导致全部登录态失效** |
| `server/uploads/` | 用户上传的图片与音频 |

建议做法：设置 `XSZ_MASTER_SECRET` 自行持有密钥，并对 `data/` 与 `uploads/` 做定时打包。

### 10.2 反向代理

置于 Nginx / Caddy 之后时：

```nginx
location / {
  proxy_pass http://127.0.0.1:8787;
  proxy_set_header Host $host;
  proxy_set_header X-Real-IP $remote_addr;
  proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
  proxy_set_header X-Forwarded-Proto $scheme;
}
```

同时设置 `XSZ_TRUST_PROXY=1`，否则按 IP 的限流与锁定会全部落在代理地址上。
**未部署代理时不要开启该项**，否则攻击者可伪造 `X-Forwarded-For` 绕过限流。

### 10.3 常见问题排查

| 现象 | 原因与处理 |
| --- | --- |
| 端口被占用 | `set PORT=8899 && start.bat` 换端口 |
| 改了源码页面没变化 | 页面来自 `web/dist`；开发用 `npm run dev`，或 `start.bat build` |
| 后台开关前台不生效 | 已修复：登录弹窗打开与后台保存时都会重新拉取配置；仍异常时强刷页面 |
| 忘记超级管理员密码 | 设置 `XSZ_ADMIN_PASS` 与 `XSZ_ADMIN_RESET=1` 后重启 |
| 登录偏慢 | PoW 首次求解所致；可在后台调低「工作量证明基础难度」 |
| 实名资料读不出来 | `master.key` 被替换或丢失，无法恢复，只能重新采集 |
| 服务端日志乱码 | 用 `start.bat` 启动（会自动切换代码页）；直接 `npm start` 时建议使用 UTF-8 终端 |
| **打开某个弹窗后整页黑屏** | 典型的渲染期崩溃（多为 Hook 被写在提前 return 之后）。顶层已加**错误边界**，会显示报错信息而不是黑屏；按提示执行 `npm run lint:hooks` 定位并修复 |

### 10.4 纯净实例与开源分发

`opensource/` 目录提供一份**只有超级管理员、不含任何其他数据**的空白实例，
适合开一个新站点，或作为开源分发时的「干净起点」。

```bash
npm run fresh                        # 生成 opensource/data
npm run fresh -- D:\mysite-data      # 生成到指定目录
set XSZ_ADMIN_PASS=你的口令 && npm run fresh
```

| 项 | 说明 |
| --- | --- |
| 超级管理员 | `huazhiyou` |
| 默认口令 | `huazhiyouyou` |
| **⚠ 首次登录后请立刻改密码** | 路径：个人信息 → 账号与安全 |
| 数据目录内容 | 只有 `xinshizhan.db` 与 `master.key`，没有任何说明文件或业务数据 |

为什么用脚本生成，而不是直接打包一个 `.db` 文件？
因为口令是用**主密钥派生的胡椒**做哈希的：只发 `.db` 不带 `master.key`，文档里的口令永远登录失败；
连 `master.key` 一起发，等于公布一把永久钥匙。`npm run fresh` 在使用者本机生成专属主密钥，
口令与密钥都只属于那一份实例。

`opensource/.gitignore` 默认忽略 `data/`（数据库 + 主密钥都不该进版本库）。
详细说明见 [`opensource/README.md`](opensource/README.md)。

### 10.5 生成开源副本

准备把整个项目发布出去时，用打包脚本生成一份**干净副本**：

```bash
npm run oss:copy                  # 输出到 ./XinShiZhan
npm run oss:copy -- MySite-OSS    # 换一个目录名
```

脚本会：

1. 只复制源码与配置 —— 跳过 `node_modules`、`web/dist`、`server/data`、`server/uploads`、
   `opensource/data`、各类日志与 `*.tsbuildinfo`；
2. 自动在副本里执行一次 `init-fresh`，生成**只有超级管理员、没有任何其他数据**的数据目录，
   并且使用这一份副本专属的**全新主密钥**（不会带上你现有实例的密钥）；
3. 打印复制结果与数据目录内容，方便核对。

副本可以独立运行：

```bash
cd XinShiZhan
npm run install:all
npm run build
npm start
```

> **发布前请再确认两件事**
>
> 1. `XinShiZhan/server/data/` 里只有 `xinshizhan.db` 与 `master.key`，数据库里只有一条超级管理员记录；
> 2. 根目录 `.gitignore` 会把 `server/data/` 挡在版本库外 —— 这是有意的。
>    一旦把 `master.key` 公开，所有拿到这份包的部署都会共享同一把主密钥，
>    一把泄露等于全部泄露。若使用者希望开箱即用，让他自己执行 `npm run fresh` 生成专属密钥更安全。
